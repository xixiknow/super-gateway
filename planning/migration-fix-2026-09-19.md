# 旧分组配置升级修复 · 2026-09-19

## 问题

已有 enforcement 绑定的旧数据库执行 `20260901000100` 时，清空绑定会触发
`group_config_content_immutable`，导致本地启动失败。原升级测试从这条迁移之后开始，
没有覆盖该场景。解除不可变触发器后，延迟执行的 enforcement 校验还会阻止删除触发器。

## 修复

`PgStorage::migrate` 为这一条历史迁移添加事务内兼容包装：先切换约束为立即检查，
临时禁用分组配置内容不可变触发器，执行原脚本，再恢复触发器。
SQLx 原有迁移锁、事务及失败回滚继续生效。历史 SQL 文件和校验和保持原样，
已完成该迁移的数据库跳过兼容包装，不需要重建数据库或清空配置。

此兼容处理由程序的迁移入口提供；直接使用未包装的 SQLx 迁移入口仍会复现原问题。

## 验证

在项目内 `.tmp/migration-regression/` 的独立 PostgreSQL 18 测试实例验证：

- 从 `20260901000100` 之前的数据库建立带 enforcement 绑定的分组配置。
- 原迁移复现不可变配置报错，失败后原绑定保留。
- 修复入口完成全部迁移，分组配置保留，旧 enforcement 工件退役。
- 再次迁移成功；启动 schema/checksum 验证成功。
- 升级后修改配置内容仍被不可变触发器拒绝。
- 既有审计退役、导出清理和备份权限断言继续通过。
- `gateway-storage` 全目标 Clippy 零警告。

本轮未运行用户数据库的升级，也未启动网关服务；用户重新执行原启动命令即可应用修复。
